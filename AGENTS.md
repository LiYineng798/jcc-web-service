# Repository Guidelines

This is the Web service repository for the JCC workspace. Make Web/API/UI changes here and commit them in this repository.

The lineup simulator at `/tools/lineup-simulator` is a standalone dark tool workspace implemented by `templates/lineup_simulator.html` and `static/tools/lineup-simulator/{app.js,style.css}`. It reads every season dynamically from `static/season-data/catalog.json` plus each season's `champions.json`, `traits.json`, and `items.json`; do not add season-id branches or restore the legacy generated simulator data path. New season-specific behavior must be driven by shared schema capabilities such as `availability.type=unlock` and `recipe.component_ids`. Item-category tabs are also data-driven and only render when the current season contains at least one item in that category. The season-library importer generates version-isolated 96px WebP images for champion/skill/item/trait icons and records them as `optimized_local_path`; simulator thumbnails must prefer those paths while hover-card splash art keeps the original large image. The simulator supports a container-responsive flat 7-by-4 hex board that must remain fully visible at every layout width, duplicate units with unique-per-champion trait contribution, three items per unit, recipe component totals, hover details, an icon-based grouped trait picker beside champion search that dims non-matches, formation import/export/share, wide-format DOM image export with an optional height-limited trait rail and optional transparent PNG background, undo/redo, and per-season local persistence. The board footer's item-selection hint is hidden while no library item is selected and must not imply that equipped items are absent. Trait summaries are ordered unique, prismatic, gold, silver, bronze, then inactive; breakpoint `style=unique` is the canonical unique-trait signal. Keep champion portraits and trait tier frames as real image elements so DOM image export can embed them reliably.

The sibling `..\jcc-db-service` repository owns PostgreSQL migrations, database import/export tooling, backups, restores, and database deployment runbooks. Do not edit database-service files from this repository. If a Web change depends on new database schema or seed data, make and deploy the DB-service change first, then commit the Web change here.

The parent `..\` directory is only a local coordination workspace and may also contain delivery artifacts such as `.sqlite3`, `.tar`, `.bundle`, or worktree files. Do not use the parent repository for normal feature commits.

For Web behavior changes, add or update focused tests under `tests/` and run at least the affected test subset with `python -m pytest -q`.

Public pages should pass explicit SEO metadata through `seo.py` and `templates/seo_head.html`. Keep login, account, admin, editor, API, hidden, and draft surfaces noindex or out of `sitemap.xml`; public detail pages should render useful first-load HTML before JavaScript hydration.

Homepage S8 return-season information is grouped under the `S8回归信息差` navigation menu in `templates/index.html`. The menu keeps the existing S8 icon and links to `/tools/special-mechanics` and `/tools/returning-equipment`.

The `/tools/special-mechanics` page is a static S8 reference page. Each card shows one rank badge for the currently visible category only, and the rank mapping is maintained in `static/special-mechanics.js` alongside the card data.

The `/tools/returning-equipment` page uses `templates/returning_equipment.html`, `static/returning-equipment.js`, `static/returning-equipment.css`, and local images under `static/returning-equipment/`. Keep these assets inside the Web repository so production deployments do not depend on files from the parent `图片/` workspace.

The `/tools/artifact-guide` page is a static S8 reference page. It shows hero-and-artifact pairing cards sourced from `神器搭配.md`, and all images are copied into the Web repository under `static/artifacts-guide/` so production deployments do not depend on the top-level `图片/` workspace.

Season reference data is served from the season library under `static/season-data/` (see `docs/season-library.md`). The library is generated from the external season archive (`ccmax资料/数据模板`) by `scripts/season_library/import_from_archive.py`; never hand-edit `static/season-data/` — fix the archive and re-import instead. S18 PBE source JSON is normalized in the archive first by `scripts/import_existing_seasons.py --season s18 --s18-json <path>`; its `charm` mechanic renders as 仙灵 with search, six-category filtering, local tier/category images, and optional upgrade/prismatic effects. S18 skill icons come from DataTFT's `images/skill/<chessId>.jpg` endpoint and must be localized before WebP generation. Champion grids use generated WebP thumbnails, while detail pages and trait-member hover cards use full `splash` art. Items without independent source art must keep a local fallback with provenance under `extensions.image_fallback_*`. `static/season-data/catalog.json` drives the homepage `资料库` menu, the mobile resource dialog, the sitemap, and the `/tools/seasons/<season_id>` pages, so adding a season to the archive plus one import command publishes it everywhere.

Every catalog season gets `/tools/seasons/<season_id>` rendered by `templates/season_reference.html`, `static/season-reference.js`, and `static/season-reference.css` (CSS class names keep their historical `s18-` prefixes). The page shows cost-grouped champion cards with search/origin/class/cost filters and a skill toggle, a trait tab split into origins and classes, and one tab per season mechanic (`wand` entries render as wand cards; `god`/`monster`/other kinds render as generic mechanic cards, including god stages and wishes). Champions tagged `new` in the archive carry the `新` badge, and `unlock`-availability champions carry a `解锁` badge.

Champion cards link to `/tools/seasons/<season_id>/champions/<champion_id>` (ids, not names — several seasons contain duplicate champion names). Detail pages are server-rendered by `season_reference_service.build_champion_detail()` from the full snapshots (`champions.json`/`traits.json`), including per-star stat and skill-variable tables when the archive has them. Hover previews and trait-member thumbnails use `static/season-champion-ui.js` on both the list and detail pages. Legacy URLs `/tools/s18-preview`, `/tools/s16-5-preview`, and `/tools/s18-preview/champions/<name>` return 301 redirects to the season-library equivalents.

On screens up to 640px wide, the champion filters are collapsed behind a summary trigger by default, champion skills start hidden, and champion cards render in a compact two-column grid. Desktop filters stay expanded and champion skills stay visible by default. Keep filter state, the filtered result count, and `aria-expanded` synchronized when changing this behavior.

On screens up to 520px wide, the homepage replaces its individual content links with the `资料` trigger and a native-dialog bottom sheet. The sheet groups the simulator, the season-library reference pages, patch notes, and the three S8 return-season references. Image mode, theme, and account controls remain directly available; desktop navigation keeps its existing individual links and S8 hover menu.

The homepage hero stat card shows all-site public regular lineup collection size from `/api/home-stats`. Current displayed result count is list context, not site context, and belongs near the list heading through `#currentDisplayCount`.

Homepage regular-lineup search uses the `.t-clear` structure in `templates/index.html` and `static/home-transitions.js`. Clearing resets query results immediately while the previous text dissolves. Uncached regular-lineup navigation requests use layout-stable skeleton cards; cache hits and copy/like/favorite refreshes must not flash the skeleton state. Live comp rankings retain their separate loading behavior.

Homepage regular lineups and live comps share numbered pagination rendered by `static/app.js`. Page counts come from each API's dynamic `total_pages`; long ranges keep the first and last page with responsive ellipses. Successful pagination requests scroll to `#listHeading`, while failed or aborted requests do not. Keep mobile pagination on one row with icon-only direction controls.

Live comp season configuration is stored in the live comp season manifest and normalized by `live_comps_helpers.py`. Admin season order changes update each season's `order` and compact the list to `1..N`. The public homepage season menu (`/api/live-comps/seasons`) and lineup create/edit season selector (`/api/lineup-seasons`) both follow this same order, while hidden or disabled seasons stay out of public/user-facing selectors.

The built-in live comp catalog includes `s16-5-legends` (`S16.5 · 英雄联盟传奇`) as an active, non-default season. Uploads and manual-code overlays use `instance/live-comps-seasons/s16-5-legends.json` and the matching season id; `s16.5` and `s16-5` are accepted aliases.

The admin sidebar exposes `阵容管理` as an expandable group with `阵容查找` and `批量导入` child entries. The lineup list loads the newest 10 rows by default and keeps server-side search/pagination; bulk import stays isolated in its own view. Admins paste one lineup-code snippet per line, choose a visible lineup season through the site's internal dropdown menu, preview parsed rows through `POST /api/admin/lineups/bulk-import/preview`, then confirm import through `POST /api/admin/lineups/bulk-import`. The importer extracts the lineup name from the first hash-delimited segment, using the text after the final hyphen when present, writes new rows as the current admin user, and skips both database-existing codes and duplicates within the same upload.

The admin console uses `templates/admin.html`, `static/admin.js`, `static/admin/core.js`, `static/admin/overview.js`, `static/admin/daily-reports.js`, and the admin-only `static/admin.css`. `admin.js` owns application state, request orchestration, expandable sidebar groups, and the remaining workspaces; `admin/core.js` owns shared DOM, escaping, formatting, and debounce helpers; `admin/overview.js` owns overview KPI, traffic chart, todo, and copy-rank rendering; `admin/daily-reports.js` owns the daily-report workspace (calendar date picker, previous/next-day navigation, a bounded recent-report strip, KPI cards, hourly heatmap, top pages, copied-code leaderboard). User management loads the newest 10 users by default with server-side pagination. The desktop sidebar exposes `实时阵容` as an expandable group with `阵容码维护` and `赛季管理`; mobile mirrors both expandable desktop groups as labeled sections in the "More" bottom sheet. Desktop uses a fixed grouped sidebar and compact top bar; mobile uses a dedicated five-item bottom navigation plus a "More" bottom sheet, so all modules remain reachable without stacking the desktop navigation. Admin shell icons come from the pinned local Lucide browser build under `static/vendor/lucide/`; do not replace it with a production CDN dependency. Keep the workbench dense, scannable, and operations-focused.

The admin overview loads the copy leaderboard during initial boot. Each ranked item includes expandable administrator-only successful-copy event details with the copier, recorded client IP address, timestamp, source page, lineup uploader, and currently available code. Live-comp season mutations treat the mutation response as authoritative and isolate follow-up refresh failures so a successful file/manifest update is not reported as an operation failure.

Season-reference skill and trait text renders stat markers as chips for physical/ability power, attack, attack speed/range, armor, magic resistance, health, critical stats, mana regeneration, omnivamp, damage amplification/reduction, and related aliases. The lineup simulator's active trait rows expose a hover detail popover with the trait description, current count, and breakpoint effects.

All pages restore the saved light/dark theme synchronously from `templates/seo_head.html` before the main stylesheet loads; keep this early initialization in place to avoid a light-theme flash during navigation. The admin overview shows the regular-lineup and live-comp portions of today's total copies, includes today's new/returning visitor mix from `/api/admin/overview`, and lets each daily UV tooltip activate across the full vertical plot column aligned with its data point.

Admin startup loads the overview and live-comp season manifest in parallel, and the settings tab loads settings and notices in parallel. The overview's seven-day UV series uses one grouped visit query with zero-filled missing dates; today and yesterday values are derived from that same series. The overview tab also loads `/api/admin/copy-rank` in parallel — a daily leaderboard of the most-copied codes across regular lineups and live comps (grouped from `copy_action_events`, enriched with lineup rows and live-comp titles).

The admin daily-report feature snapshots one calendar day's activity into `daily_admin_reports` (one row per `report_date`, headline totals denormalized, full report in `payload_json`). `daily_report_service.py` owns aggregation and persistence: summary UV/PV and new/returning visitors (plus 3-day/7-day return windows), registrations, successful logins, successful copies (regular + live comp from `copy_action_events`), new lineups, guestbook, reports, likes, favorites, 24-hour UV/PV/copy series for the heatmap, top pages, top copied codes, a season/version copy rank (`season_copy_rank`), a top visitor-IP panel (`top_visitor_ips`, admin-only), and deltas versus the most recent earlier report. `daily_report_worker.py` starts one daemon thread per Flask process and auto-generates yesterday's report shortly after midnight (insert-or-ignore makes concurrent workers idempotent); tests disable it via `TESTING`. Admin routes are `GET /api/admin/daily-reports`, `GET /api/admin/daily-reports/<date>`, and `POST /api/admin/daily-reports/<date>/generate` (CSRF-protected, writes an audit log). Manual backfills use `scripts/maintenance/generate_daily_report.py --date YYYY-MM-DD [--force]`. The SQLite table and index live in `db_schema.py`/`db_migrations.py` and mirror `jcc-db-service` migration `0007_daily_reports.sql`; keep them aligned.

The admin live-comps workspace can create new live-comp seasons through `POST /api/admin/live-comps/seasons` (dialog next to 赛季管理; slug id + name + status, hidden-by-default recommended until data is uploaded) and can refresh the public updated_at of the selected season via `POST /api/admin/live-comps/seasons/<season_id>/touch-updated-at`, which bumps the season data file's mtime (per season; errors if the season has no data file yet).

Performance conventions (2-core/2GB host): production runs gunicorn via `deploy/gunicorn.conf.py` (2 gthread workers x 4 threads) behind nginx, which serves `/static/` directly with long cache lifetimes and gzip — keep `deploy/nginx.conf.example` and `deploy/jcc.service.example` in sync with the live configs. Site JS/CSS references in templates must go through the `static_v()` template global (auto mtime stamp) so cached assets refresh on deploy. Mutable `static/season-data/**/*.json` files must use `max-age=0, must-revalidate`; the simulator also appends one content-derived `season_data_stamp()` to the catalog and season JSON URLs, while season-data image URLs carry `?v=<version_id>`. PostgreSQL connections come from a small `psycopg_pool` in `db.py`. Page-view tracking only records logged-in users or guests that echoed the visitor cookie, and skips bot user agents; a genuine visitor's first page view is uncounted by design. Query caches in `lineup_cache.py` are bounded LRUs whose revision lives on the entry (score-style caches tolerate a 10s-stale revision in production). Event tables are pruned manually via `scripts/maintenance/prune_events.py` (dry-run by default, never scheduled automatically). Admin date filters use half-open `created_at >= ? AND < ?` ranges — never `LIKE 'day%'` or `substr()` — and new indexes must be added both to `db_schema.EXTRA_INDEX_STATEMENTS` (SQLite) and a `jcc-db-service` migration (PostgreSQL).
