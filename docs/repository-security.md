# 仓库发布安全

## 公开与私有边界

可以公开：业务源码、测试、依赖锁文件、正式 migrations、去敏后的部署模板、通用维护流程、
运行需要的静态图片/赛季基准、前端构建产物及许可证。不能仅因文件较旧或是生成文件就删除。

不能公开：真实环境文件和连接串、API key/token、私钥/证书、数据库/备份、用户数据与日志、
私有赛季源包、真实主机 IP/内网拓扑、运维账号、真实部署/备份路径、恢复点索引与生产验收记录。
站点的公开域名不等于密码，但公共模板和测试仍统一使用保留域名，不绑定某个维护者的站点。
操作指南描述“如何部署”，不要描述“谁在哪台机器何时部署、备份放在哪里”。

- 域名用 `jcc.example.com`、`database.example.com`；IP 用 loopback 或 RFC 5737 文档网段。
- 配置值优先通过环境变量提供；示例密码使用明显占位值，绝不能复制到生产。
- 真实运维资料放受限的外部知识库/密码管理系统。临时本地资料放 `private/`，实际环境文件可用 `.env`、`.env.production`。
- `.gitignore` 不是访问控制：本地文件仍可能被打包、截图或复制；`private/` 也不是异机备份。
- 不把 secrets 放进 issue、PR 正文、CI 日志或截图；审查报告只给文件路径、规则、行号，不复述秘密。

## 提交与推送前检查

在**各自服务仓库**执行，不能在协调目录执行：

```bash
python scripts/check_repository_safety.py --worktree
# 人工确认需要的文件后，只暂存本次改动，不使用 git add -f。
git add <reviewed-paths>
python scripts/check_repository_safety.py
git diff --cached --check
git diff --cached --stat
# 在本地受控终端检查完整 diff；不要把可能含秘密的输出贴到公共平台。
git diff --cached
```

Web 的旧命令 `python scripts/maintenance/check_deploy_safety.py` 保留，转发到同一检查器，也支持 `--worktree`。

默认模式检查**完整 Git 索引的实际 blob**，不是仅文件名、不是磁盘上的最新文本，避免“已暂存秘密、随后仅修改工作副本”漏检。
`--worktree` 检查跟踪文件和未忽略的新文件，用于暂存前检查；它不读取已忽略的私有目录。
已跟踪的文件即使匹配 `.gitignore`，仍然会被检查；已暂存删除的文件不会误报。
检测器失败返回非零状态，输出只包含路径、行号和规则，不打印命中的秘密。

检查覆盖敏感文件类型/目录、私钥头、部分常见 token、带非占位口令的 URL，
以及文档/配置中的非示例 IPv4、代码 URL 中的 IPv4 和部分个人工作站路径。
测试中的单纯 IP 字符串和游戏数据/矢量数值不会一律当作服务器地址；测试并不豁免凭据检测。
**这是轻量规则防线，不是完整 secret scanner**：不覆盖所有供应商令牌、IPv6、任意硬编码口令、
任意自定义域名/路径、编码/压缩内容、图片中的信息或历史提交，必须结合人工审查和平台 secret scanning。

`.github/workflows/repository-safety.yml` 在 push/PR 上重跑相同检查和检测器测试，权限只读。
**CI 发生在内容上传之后，不能追回泄露**；真正的事前防线是本地暂存检查。
管理员可在 GitHub 将该检查设为必需状态；仓库内新增 workflow 不会自动配置分支保护。

## 已跟踪资料和历史泄露

增加忽略规则不会自动停止跟踪，更不会删除历史。对确认不应发布的文件：

1. 先保存受控私有副本，确认不影响运行/恢复，再在隔离分支用 `git rm --cached -- <path>` 停止跟踪；文件仍保留在本机。
2. 同时去掉公开文档对私有文件的链接，补充通用模板和忽略规则。不要让忽略规则屏蔽 migrations、源码或合法构建产物。
3. 若曾上传有效密码、token 或私钥，**先撤销/轮换**，核查使用记录和影响；删文件、私有化仓库或删除最新提交都不足以使凭据失效。
4. 在受控环境核查所有已发布分支/tag/历史路径，以及 release 附件、Actions 日志、PR、fork、缓存和其他克隆。检测器的默认通过不表示历史安全。
5. 历史重写、强推、删除远端分支和附件须另行审批、备份和协作通知。确有需要时由维护者使用 `git filter-repo` 等工具制定完整清除范围，并联系托管平台处理缓存；不能只清 main 或依赖一次普通删除提交。
6. 历史改写后旧克隆可能重新引入旧内容；协作者按协调方案重新克隆或清理，不直接把旧分支推回。

## 判断冗余文件

先核查运行引用、模板/路由、CLI 调用、测试、构建输入输出和外部兼容承诺，再决定删除。

- 生产部署纪要和恢复点索引不应充当公共文档，迁至私有系统；通用运维流程和模板继续保留。
- 已应用 SQL migration 是升级链，不能删改；旧链接依赖的页面、旧生成器及 CLI 仍可能有使用者。
- 前端源码与对应 JS/CSS/许可证、运行时静态 JSON/图片是交付契约，不是重复文件。
- 无法证明废弃的文件宁可标注职责，不顺带删除；其他 worktree、未提交草稿、顶层数据库和交付目录不在清理范围内。
