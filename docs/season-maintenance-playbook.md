# 赛季创建、版本更新与补丁操作规程

这是后续管理员和 AI 执行赛季维护时的首读流程。以实际代码能力为准，不把规划功能描述成已实现。协议细节见 [资料包设计](season-upload-package-design.md)，服务器配置见 [部署手册](season-package-operations.md)。

## 先判定任务类型

| 用户要求 | 应执行的流程 | 是否需要部署代码 |
| --- | --- | --- |
| 新增从未登记的赛季，如未来的 S19 | 本文「新赛季首次接入」 | 需要首次登记、采集适配和基础资源部署 |
| 已登记赛季更新到官方新补丁 | 本文「官方补丁更新」 | 已支持的数据能力通常不需要 |
| 同一官方补丁下修正文案、图片、回合或条件 | 本文「资料修订」 | 不需要，只提高资料修订号 |
| 官方发布带新版本字符串的热修 | 官方补丁更新，保留真实版本字符串 | 通常不需要 |
| 新的模拟器交互、计算规则或未知玩法展示模板 | 先实现并部署所需能力，再发布数据 | 需要 |
| 更新热门阵容、阵容码、公告 | 使用各自原有后台 | 不由赛季 ZIP 自动更新 |

用户已决定暂不做压缩优化：继续使用完整 ZIP（JSON、所有被引用图片、来源、说明），不添加增量包、图片复用或压缩协议。当前源图质量保留。数据包不执行 SQL 或脚本。

## 标识与关联，不能混用

| 名称 | 示例 | 来源与作用 |
| --- | --- | --- |
| 资料赛季 ID | `s18` | `static/season-data/catalog.json` 首次登记；资料库和模拟器共用 |
| 阵容分类 ID | 旧 S17 为 `s17-star-god` | 后台「实时阵容 → 赛季管理」；普通阵容共用这一分类 |
| 官方标识 | mode / set_id / season_code | 从真实官方版本记录读取，不能根据站内名字猜测 |
| 游戏补丁 | `18.18.2` | 官方版本字符串 |
| 资料修订 | `data_revision: 2` | 同一补丁重新制作内容时递增 |
| 发布修订 | `active.revision` | 服务器维护的并发控制号，每次切换递增；不要当成资料修订手工指定 |

当前 S18 资料的官方客户端代号为 S19，这不代表应把站内 S18 改名为 S19。模拟器和资料库共享同一赛季的当前发布包，但两边展示状态、顺序独立；模拟器默认赛季也独立于首页实时阵容默认赛季。

实时阵容上传记录的 `formationDetails.season_id` 必须使用资料赛季 ID，弈子和装备 ID 必须能在该资料中解析；原始英雄 ID 需要同包 `tft-codebook.json` 映射。仅把两个目录的中文名字改成一样不会建立关联。新整数赛季可以都用 `s19` 简化命名，但仍需分别登记。

普通阵容没有单独的「创建赛季」入口；阵容分类启用后即成为普通阵容创建/编辑/批量导入的可选项。普通/实时金铲铲码只提取格式，不自动核验其真实游戏赛季；分类选错不会转换游戏码。模拟器 `JCC2-` 是本站分享码，不能直接作为游戏码使用。资料字典变化可能使旧 JCC2 码不兼容，必须在验收时检查。

## 执行前检查

1. 查看工作目录及 `git status`，使用 Web、DB 各自服务仓库；用户要求 worktree 时继续在对应 worktree。不要向协调目录的 Git 提交服务变更。
2. 查阅当前后台发布记录：目标赛季、实际补丁、资料修订、当前 release_id，以及两个展示配置。只读检查不等于允许部署生产或上传测试资料。
3. 确认首次功能部署已完成：DB 0015 → Web → 独立 season worker；两者共享数据库和持久资料目录。否则先按部署手册处理，不能假定 worktree 提交已上线。
4. 确认源档案及专用输出目录，避免覆盖其他任务的制作结果。生产数据库、`.env`、ZIP、图片缓存和凭据不入 Git。
5. 只访问官方来源；禁止 DataTFT 网络抓取。仙灵回合/条件可沿用本地历史第三方补充，必须保留来源和未核验状态。

## 新赛季首次接入

1. **适配本地采集。** 在外部 `ccmax资料/数据模板` 查阅 `docs/官方数据源与版本更新指南.md`。现有 `scripts/import_existing_seasons.py` 只登记 S8/S16.5/S17/S18；未来 S19 不能直接改命令参数执行。需增加真实官方映射、builder、CLI choices、档案 catalog 及必要的校验支持。官方 mode 和客户端代号以当时官方记录为准。
2. **准备完整档案。** 保存原始官方快照、JSON、图片和来源，校验成功。无特殊玩法明确留空；有多个玩法分别登记。新资料展示优先使用现有 cards/variants/stages/table 模板；新的模拟器行为需代码能力支持。
3. **在 Web 首次登记为隐藏。** 下面命令仅在档案库已经存在 `s19` 且网站 catalog 尚无 `s19` 后执行。命令在 Web 仓库运行；用真实的档案路径替换示例。

```powershell
python scripts/season_library/import_from_archive.py --source "D:/本地档案/数据模板" --season s19 --official-only --initial-status hidden
```

该命令生成 `static/season-data/s19` 并更新 catalog。`--initial-status` 只接受新登记的单个赛季；目标已经存在时会拒绝，避免意外覆盖旧数据。默认展示策略尊重 catalog 的 hidden/disabled/archived/active，管理员后续配置优先。原有目录缺少有效状态时不自动公开。

4. **校验和部署首次资料。** 检查生成的目录、名称、ID、版本、数量、图片引用和隐藏状态；运行测试，将 Web 首次资料登记提交并部署。若没有新数据库结构，这次登记无需新增 DB migration。不要仅部署 catalog 而遗漏它引用的基础资源。
5. **保存独立初始包。** 使用下一节打包步骤生成 r1。后台「赛季版本更新」上传、预览并发布；此时赛季仍隐藏。初始包保存了可独立回滚的快照，不能只依赖随未来代码部署变化的静态基准。
6. **启用资料页面。** 在「资料库赛季」和「模拟器赛季」分别启用，按需排序或设置模拟器默认赛季。首次启用后直接检查资料页、弈子详情、模拟器和首页资料菜单。
7. **创建阵容分类。** 后台「实时阵容 → 赛季管理 → 新增赛季」，填写 ID、名称、说明，先选择后台隐藏。此操作不替代资料登记，也不生成资料 ZIP。
8. **上传实时阵容。** 用「实时阵容 → 数据上传」选择该分类，上传 JSON、预览、启动处理；详情 `formationDetails.season_id` 指向资料 ID。模板见 [实时阵容上传格式](live-comps-upload-schema.md)。核对后启用分类，按需设默认。普通阵容选项随后出现，无需另建赛季。
9. **创建普通阵容并验收。** 新增一条明确属于该赛季的有效游戏码，或在「阵容管理 → 批量导入」预览后写入；检查筛选、复制、站位详情和关联图片。公告/公开更新日志按实际需要单独发布。

新赛季的正式上线上述步骤仍有两套目录，并非一个 ZIP 自动创建所有入口。当前没有统一赛季登记后台，不得声称已经实现。

## 官方补丁更新（已有赛季）

1. **更新本地档案。** 在档案库运行（下面以 S18 举例）：

```powershell
python scripts/import_existing_seasons.py --season s18
python scripts/validate.py --all
```

明确更新指定补丁时加 `--version <官方真实版本字符串>`；核实生成的版本和生效时间。该脚本输出是档案，不是可直接上传的网站包。不要用 PBE 参数替代正式服资料。

2. **生成网站资料。** 回到 Web 仓库，输出到独立制作目录：

```powershell
python scripts/season_library/import_from_archive.py --source "D:/本地档案/数据模板" --season s18 --official-only --output-root "D:/jcc-prepared"
```

`--official-only` 跳过第三方回合观察网络请求；此转换阶段仍可能取缺失的官方强化符文或图片。最终打包和服务器导入完全离线。保留归档补充来源，不把继承字段标成已经确认的当前官方规则。目标根目录下所选赛季目录会重建，必须是专用目录。

3. **写更新说明。** 复制 [说明模板](examples/season-release-notes.json)，按本次真实变化填写 `title/summary/sections`；有额外来源记录时按 [来源模板](examples/season-provenance.json) 填写并传入 `--provenance`。这些说明供管理员审核，不会自动成为公开公告。
4. **生成完整包。** 下面的 3 是示例，应选未使用的资料修订号：

```powershell
python scripts/season_library/build_upload_package.py --season s18 --source "D:/jcc-prepared/s18" --revision 3 --notes "D:/jcc-prepared/release-notes.json" --output "D:/jcc-packages/s18-r3.zip"
```

游戏版本从资料中读取，文件名不决定补丁。新游戏补丁可从 r1 开始，同一补丁修改内容必须递增。源目录必须包含完整 JSON 和图片；打包器负责清单与哈希，不要手工修改 ZIP 内文件。重复传输使用原 ZIP。
5. **上传并预览。** 「赛季版本更新」选择 ZIP，等待校验完成；检查数量、资料差异、玩法与来源、告警，打开两个预览。界面一次显示一个上传文件，连续上传可先移除旧文件行；这只清除上传列表，不删除历史版本。
6. **审核发布。** 若提示线上修订已变化，先重新比较，再审核；不要重试携带旧发布修订号的请求。发布成功后刷新页面，无需 Git 推送、DB 迁移或重启。
7. **完成前台验收并记录。** 使用本文验收清单。若失败，回滚到明确的已发布快照；不要手改 active 表或解包目录。保存包 ID、游戏版本、资料修订、发布结果和检查记录。

## 同一补丁的资料修订

例如官方仍是 `18.18.2`，仅修正图片、数值录入、文字或沿用的条件：

1. 在本地资料源修正，并更新来源/核验信息；需要转换时重新输出网站资料。
2. 保持真实 `game_version` 不变，提高 `data_revision`，重新生成完整 ZIP。
3. 重走上传、校验、预览、发布和验收。不要新增一个「S18-r3」赛季，不要把普通阵容记录的编辑 `version` 当成游戏补丁。

若游戏官方公布了新热修版本号，则保留该真实版本号，按官方补丁流程处理。不能通过改文件名伪造补丁版本。

## 每次发布必须核对

- 管理员预览命中新 release_id，访客无法访问候选资料；预览不能写业务数据。
- 资料库与模拟器 catalog 中，同一赛季的 release_id/data_root/asset_root 一致；版本、数量和必要的图片正确。
- 弈子详情、装备与羁绊有效；模拟器能上阵、装装备、统计羁绊。链接 `?season_id=...` 指定赛季优先于浏览器记住的赛季，分享码自己的赛季优先级更高。
- 无玩法时不出现旧玩法；增加/修改/删除玩法符合本次快照；继承条件有明确告警。
- 首页桌面/手机资料入口、模拟器选择、首页阵容筛选、普通阵容选择符合各自展示配置。
- 实时详情 ID 可解析；榜单头像与英雄条仍使用独立上传缓存，不会随资料包自动刷新。普通/实时游戏码不会被资料发布改写。
- sitemap 在发布/回滚/隐藏后反映新的公开季和弈子列表。服务器各 worker 会根据当前资料版本和可见性刷新缓存。
- 至少验证一次回滚：旧快照资料恢复，但业务阵容和用户数据保持原样。默认赛季和展示状态不随资料回滚。
- 生产从浏览器经过 Nginx 再验收一次。`/season-assets/` 以及需要隐藏访问控制的 `/static/season-data/` 必须经过 Flask；公开 Nginx alias 会绕过应用权限。测试客户端通过不等于生产代理配置正确。

## 可复用离线演练

演练 ID 固定 `s99`，显示为「S99 本地演练（复制 S18）」，**不是真实新赛季**。它复制现有完整 S18 资料及图片，制作 3 个完整包：初始无玩法、下一补丁新增弈子/两种玩法、同补丁 r2 修正数值并移除一种玩法。全程临时 SQLite、临时 catalog、临时文件，结束清理；不能拿这些 ZIP 上生产。

```powershell
python -m pytest -q tests/test_season_lifecycle.py tests/test_season_registration.py
```

同一个 Web worktree 同时只运行一个 pytest 进程。现有通用测试 fixture 共用 `test-lineups.sqlite3` 等固定路径，并行启动另一轮 pytest 会出现文件占用；这与使用独立临时目录的浏览器演练不同。

该测试验证未登记拒绝、独立阵容分类、新季隐藏、候选权限、完整上传与 worker、两个展示入口、实时 JSON 上传、普通阵容创建、并发修订冲突、发布、回滚、站点地图和 S18 不受影响。仅重定向资料根目录，未模拟验证器、数据库或发布逻辑；静态登记步骤由临时 catalog 写入代替真正代码部署。采集适配需在真实新季到来时另行验收。

浏览器端到端演练需要 Node 可解析 Playwright 且已经安装 Chromium/WebKit：

```powershell
node tests/season_lifecycle.browser.cjs
```

它为每个浏览器自动启动独立 loopback 服务器及真实处理线程，结束关闭。截图保存到忽略目录 `instance/season-lifecycle-checks/`，不提交资料包、数据库或日志。测试的金铲铲码明确为无效演练字符串，仅验证存储与流程，不证明游戏内可用。

人工查看使用：

```powershell
python tests/serve_season_lifecycle.py --port 5097
```

启动完成后访问 `http://127.0.0.1:5097/admin`，本地测试账号 `previewadmin / Preview1234`；终端输出 3 个临时 ZIP 路径。退出进程会清除该轮资料。生产始终使用独立 `season_package_worker.py`，此处同进程线程只用于测试。

## AI 交付要求

交付时写清：任务类型、两个赛季 ID、真实官方版本、资料修订、沿用字段来源、是否存在新能力、修改的仓库和提交、实际执行的测试、发布/回滚记录、是否已部署。没有真实 PostgreSQL 或生产代理验收时必须明确说明。不要把本地演练或 Git 提交描述为生产上线；不要因测试未覆盖新游戏规则就声称任意未来赛季无需适配。
