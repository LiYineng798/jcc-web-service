# 项目重构路线图

## 目标

把当前项目从“功能可用但文件偏大、脚本偏散、部署依赖人工判断”整理成“结构清晰、边界明确、方便继续迭代”的状态。

## 重构顺序

### 第 1 阶段：先稳住入口与部署

- 固定 `run_server.py`、`deploy/`、服务器更新脚本、数据库备份脚本的行为
- 明确开发、同步、部署、回滚的标准流程
- 确保服务器更新前先备份数据库

目的：先把最影响稳定性的链路定住，后面重构才不会放大风险。

### 第 2 阶段：拆大文件

优先拆这些文件：

- `admin.py`
- `live_comps.py`
- `static/admin.js`

建议拆法：

- 后端按 `routes / services / repositories` 分层
- 前端后台按模块拆成多个小文件

目的：降低单文件复杂度，减少后续改动的连锁影响。

### 第 3 阶段：统一数据边界

先统一这些核心概念：

- 赛季
- 普通阵容
- 实时阵容
- 手动补码
- 举报
- UV / 增长数据

重点整理：

- `seasons.py`
- `lineups.py`
- `live_comps.py`

目的：避免同一概念在不同文件里有不同写法。

### 第 4 阶段：脚本与服务分区

把内容明确分成两类：

- **服务端运行代码**：部署到服务器后实际对外提供服务的部分
- **本地工具脚本**：抓取、转换、上传、刷新时间等本地执行工具

建议：

- 服务器部署只保留服务端必要文件
- 本地脚本放到独立工具目录
- 不把抓取工具混进线上运行主链路

目的：以后同步 GitHub、更新服务器时更清楚，不容易误上传无关脚本。

### 第 5 阶段：补测试与回归保护

重点补这些测试：

- 后台 API
- 实时阵容
- 赛季切换
- 手动补码
- 部署脚本

目的：保证后续重构时，老功能不会被悄悄改坏。

## 推荐执行顺序

1. 部署与备份流程
2. `admin.py` / `live_comps.py` 拆分
3. `static/admin.js` 拆分
4. 数据边界统一
5. 脚本与服务分区
6. 测试补齐

## 当前判断

- 项目功能已经比较完整
- 当前主要矛盾不是缺功能，而是结构增长过快
- 最容易出问题的点是：大文件、重复逻辑、脚本与服务混杂、更新流程依赖人工判断

## 预期结果

重构完成后，项目应该达到：

- 后端文件更小、更清晰
- 前端后台更容易改
- 本地工具和线上服务边界更清楚
- 服务器更新流程更稳
- 后续新增功能成本更低
